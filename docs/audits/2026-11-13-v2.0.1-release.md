## Corrección incluida

El adaptador de Vercel contabilizaba retrospectivamente una tool call del estado anterior después de `transitionTo()`. Con `maxConsecutiveTools: 1`, `validate_dni` transicionaba IDENTITY → BOOKING, el presupuesto se reiniciaba, pero el adaptador volvía a contar `validate_dni` en BOOKING y devolvía `toolChoice: 'none'`. `check_availability` nunca se ejecutaba.

La corrección usa la revisión monotónica del FSM: si la revisión cambió desde el último `prepareStep`, el adaptador salta las llamadas históricas y no las imputa al estado nuevo. No se añadió un ejecutor ni se rediseñó el presupuesto.

## Tests de regresión

- `tests/vercel-generate-text.test.ts`: `generateText` + `MockLanguageModelV3`, `loopShield.maxConsecutiveTools = 1`, `validate_dni` → BOOKING, `check_availability` disponible y ejecutada.
- `tests/vercel-prepare-step.test.ts`: el mismo caso a nivel `prepareStep`; y un flujo sin cambio de estado que sigue devolviendo `toolChoice: 'none'` al alcanzar el límite.

## Riesgos residuales

- El budget sigue siendo admisión entre pasos; varias tool calls del mismo paso pueden superarlo.
- Solo Vercel tiene test de runtime; OpenAI, Anthropic, LangChain y Gemini son experimentales.
- No se ejecutaron APIs reales de proveedores; se usó `MockLanguageModelV3`.
- `streamText` no está cubierto.
- El adaptador de Vercel construye el `ToolSet` completo; `build()` debe ser puro.
- La publicación npm requiere configurar el Trusted Publisher y el environment `npm`.

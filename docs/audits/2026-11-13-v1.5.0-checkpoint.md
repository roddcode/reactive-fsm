## Cambios de contrato

1. **`config.tools` es la autoridad.** Un tool que está en `registry.gates` pero no en `config.tools` deja de anunciarse. Es una corrección del contrato documentado, pero cambia el comportamiento de quien dependía del registry como única fuente.
2. **El adaptador de Vercel cambió de forma.** `inject().tools` ahora contiene el `ToolSet` completo; `prepareStep` devuelve `activeTools` con la intersección del estado, `gates` y `condition`. Ya no muta el objeto `tools`.
3. **Las transiciones async obsoletas se rechazan.** Una transición cuyo guard termina después de que el estado cambió lanza un error. Incluye A → B → A mediante revisión monotónica.
4. **Se eliminaron los peers de proveedores.** El paquete no tiene dependencias de runtime ni peers. `ai` y `zod` son solo `devDependencies` para los tests de tipos/runtime.
5. **Node 20+.** Node 18 está EOL y Vitest 4 no lo soporta.

## SemVer: por qué 1.5.0 y no 2.0.0

La decisión es explícita, no automática:

- Los contratos que cambian (`config.tools`, gating de Vercel, rechazo de transiciones obsoletas) estaban **documentados pero no implementados** en `1.4.1`. El adaptador de Vercel no funcionaba con su peer declarado (`ai@4`), así que no hay una ruta de consumidor funcional que preservar.
- No se ha demostrado adopción externa relevante (1 star, 0 issues, 75 descargas/mes). Eso no prueba que no existan usuarios, pero reduce el riesgo de una corrección de contrato.
- Aun así, un consumidor que dependiera del registry como autoridad o inspeccionara `inject().tools` puede romperse. Por eso el `CHANGELOG` lo marca como cambio de comportamiento y este documento lo hace visible.

**Recomendación:** `1.5.0` como release de estabilización, con notas de migración. Si se prefiere SemVer estricto para cambios de comportamiento, la alternativa es `2.0.0`; en ese caso la reducción de alcance de la Etapa 3 pasaría a `3.0.0`.

## Riesgos residuales

- **Tool budget no estricto dentro de un paso.** `prepareStep` comprueba antes del siguiente paso. Si el modelo pide cuatro tools en un paso y quedan dos, las cuatro pueden ejecutarse. Es un presupuesto de admisión entre pasos, no un límite transaccional. Está documentado en README y CHANGELOG.
- **Solo Vercel tiene test de runtime.** OpenAI, Anthropic, LangChain y Gemini siguen siendo experimentales; no se ejecutaron contra APIs reales.
- **`build()` se ejecuta para todo el registry en Vercel.** El adaptador construye el `ToolSet` completo para que `activeTools` pueda habilitar tools de estados futuros. `build()` debe ser una fábrica pura y segura para cualquier estado; no debe ejecutar efectos.
- **Streaming no probado.** El test de integración usa `generateText`, no `streamText`.
- **P2 pendiente.** `prompts`, `schema`/`validateWith`, `toMermaid`, `currentStateGroup` y la reducción de adaptadores no forman parte de P0.
- **Publicación npm pendiente.** El token local sigue inválido (`401`); el release puede prepararse y etiquetarse, pero no publicarse hasta reautenticar.

## Correcciones a la auditoría de 1.4.1

- “No es un FSM” es excesivo: es un **FSM mínimo sin tabla explícita de transiciones**. La crítica es correcta; el nombre `reactive-fsm` se mantiene.
- “No hay usuarios externos” no es demostrable: se corrige a **“no se ha demostrado adopción externa relevante”**.
- El test D04 propuesto en la auditoría usaba `await first` y luego esperaba el estado final; con la corrección, `first` debe rechazar. La versión correcta está en `tests/async-transitions.test.ts`.
- El ADR ahora declara que fue **propuesto por el agente** y aceptado por el mantenedor, en lugar de atribuir la decisión directamente.
- La afirmación del CHANGELOG sobre CI está respaldada por el run `43472884321`.

## 1. Veredicto

El núcleo es pequeño, legible y coherente para lo que hace, pero no es un FSM ni un mecanismo de control determinista: es un contenedor mutable de estado con un filtro de herramientas. Cualquier estado válido puede transicionar a cualquier otro si el guard lo permite, y los adaptadores solo formatean definiciones.

Los tres problemas más importantes:

1. **No se puede instalar junto a los SDK actuales.** Los peers `ai@^4`, `openai@^4`, `@anthropic-ai/sdk@^0.30`, `langchain@^0.3` y `@google/generative-ai@^0.21` producen `ERESOLVE` con `ai@7.0.171`, `openai@7.56.0`, `@anthropic-ai/sdk@1.8.0`, `langchain@1.6.5` y el último legacy de Google. Los adaptadores ni siquiera importan esos paquetes.
2. **El gating tiene dos fuentes de verdad y es advisory.** `config.tools` alimenta `fsm.allowedTools`, pero los adaptadores construyen desde `registry.gates` y nunca leen `allowedTools`. Nada envuelve la ejecución; la librería sugiere, no autoriza.
3. **La integración automática está rota y las transiciones async pueden pisarse.** Vercel entrega `prepareStep`, pero `ai@4` usa `experimental_prepareStep`; en `ai@7` el peer impide instalar y el tipo `Record<string, unknown>` no satisface `ToolSet`. Además, A→B con guard pendiente, A→C, terminó en B.

**Fortaleza real:** la idea de una política pequeña de herramientas por estado, sin dependencias de runtime, es clara; el paquete pesa 13 kB, compila, 96 tests pasan y el tarball publicado coincide con el build local.

**Confiabilidad:** no usaría la versión actual como control de operaciones críticas. Como ayuda de selección de herramientas, solo con autorización y validación en la aplicación.

**Utilidad diferenciada:** potencial, no demostrada. AI SDK 7 y OpenAI Agents SDK ya ofrecen controles nativos; el código propio suele bastar.

**Inversión:** acotada a corregir los P0, sostener una integración real y un caso de uso. Nada de nuevas funcionalidades hasta que eso demuestre valor.

## 3. Arquitectura real

```text
App
 ├─ createFSM(config)
 │    ├─ valida initialState / snapshot / fallbackState
 │    ├─ _currentState mutable
 │    ├─ _context = shallow copy
 │    └─ loop shield (contador)
 ├─ registry: ToolEntry[]  (name, gates, condition, build)
 ├─ createXAdapter(fsm, registry, context)
 │    └─ buildToolsForGate(fsm.currentState, ctx, registry)
 │         ├─ filter(entry.gates.includes(gate))
 │         ├─ filter(entry.condition?.(ctx) !== false)
 │         └─ build(ctx)  ← forma específica del proveedor
 ├─ llamada al SDK con las tools formateadas
 ├─ el modelo devuelve tool calls
 ├─ la app ejecuta las tools (fuera de la librería)
 └─ la app llama registerToolCall / refreshGate / transitionTo
```

| Capacidad | Implementación observada |
|---|---|
| Estados válidos | `Set` de `config.states`; no hay tabla de transiciones |
| Transiciones permitidas | Cualquier estado válido; solo el `guard` puede bloquear |
| Guard síncrono | `transitionTo`; solo bloquea con `=== false` |
| Guard asíncrono | `transitionToAsync`; espera el guard, pero no protege concurrencia |
| Atomicidad | No garantizada |
| Snapshot | Solo `{ state }`; no guarda contexto ni contadores |
| Herramientas del FSM | `config.tools[currentState] ?? []` |
| Herramientas del adaptador | `registry` filtrado por `gates` y `condition` |
| Validación de argumentos | `validateWith()` existe, pero ningún adaptador la llama |
| Prompts por estado | Se guardan, pero no se exponen ni se consumen |
| Loop shield | Contador de llamadas; no inspecciona resultados ni progreso |
| Concurrencia | Ninguna serialización ni control de versión |
| Dependencias de proveedor | Cero imports de SDK; los adaptadores son formateadores |

Decisiones técnicas principales:

- **Cero dependencias de runtime.** `dependencies` está vacío y `src` no importa ningún SDK. Los peers son otra cosa.
- **Sin tabla de transiciones.** `states` es solo un conjunto de pertenencia. La librería no es un motor de grafos.
- **Registro separado del FSM.** `createFSM` no conoce el registry; el adaptador no conoce `config.tools`. Esa separación produce las dos fuentes de verdad.
- **`build()` específico por proveedor.** OpenAI espera un `ChatCompletionTool` completo; Anthropic y Gemini leen `name`, `description` y `parameters`; Vercel usa el objeto tal cual; LangChain devuelve un mapa. Un mismo registry no sirve para los cinco.
- **`FSMInstance` filtra los métodos internos.** `createFSM` devuelve `FSMInstance`, que incluye `_registerToolCall`, `_resetLoopShield`, `_setState` y `_setStateAsync`. `index.ts` no exporta el tipo, pero el retorno lo filtra igual.
- **`createBaseAdapter` castea `FSMPublic` a `FSMInstance`.** Los adaptadores aceptan la interfaz pública, pero en runtime necesitan los métodos internos.

### Probables

- **Vercel AI SDK 7 en runtime:** el adaptador muta el objeto `tools` en lugar de devolver `activeTools` o un `ToolSet` desde `prepareStep`. La documentación de AI SDK 7 muestra `activeTools`; que la mutación in-place sea observada por el SDK no está verificado.
- **OpenAI/Anthropic/Gemini con sus versiones actuales:** las formas son plausibles para las versiones declaradas, pero no se ejecutaron llamadas reales.
- **Mermaid con estados `:`:** la salida es ambigua; el colapso de `SCHEDULING:date` y `SCHEDULING:time` es probable según la sintaxis `stateId: label`.
- **Causa del fallo de CI en Node 20:** el job falla en `actions/setup-node@v4`; pnpm `11.1.3` declara `node >=22.13`, y `setup-node` con `cache: pnpm` ejecuta pnpm.

## 5. Adaptadores

| Adaptador | Qué hace realmente | Integración con el run loop | Veredicto |
|---|---|---|---|
| Vercel AI SDK | Construye un mapa mutable y devuelve `prepareStep`; asume `ai@4` pero nombra el hook mal | Parcial; solo `generateText`, y solo si el consumidor renombra el hook | **Reparar — prioridad 1** |
| OpenAI | `Object.values(buildToolsForGate(...))`; métodos manuales de shield | No; formateador | **Mantener / reparación ligera** |
| Anthropic | Mapea a `{name, description, input_schema}` | No; formateador | **Mantener / reparación ligera** |
| LangChain | Devuelve un mapa y alias de callbacks | No; `bindTools` espera un array | **Retirar** |
| Gemini | Envuelve `functionDeclarations`; SDK legacy | No; formateador | **Retirar o portar a `@google/genai`** |

Mismatches confirmados contra los typings instalados:

| Área | El adaptador asume | El SDK espera |
|---|---|---|
| Hook Vercel | `prepareStep` (`vercel-ai.ts:17`) | `experimental_prepareStep` en `ai@4`; `prepareStep` en `ai@5+` |
| Disponibilidad por step | Mutar `tools` | `experimental_activeTools` en `ai@4`; `activeTools` en `ai@5+` |
| Tool Vercel | `parameters` | `parameters: ZodTypeAny \| Schema<any>` en `ai@4`; `inputSchema` en `ai@5+` |
| Tools OpenAI | `unknown[]` | `Array<ChatCompletionTool>` |
| Tools Anthropic | `unknown[]` | `Array<Tool>` con `input_schema` |
| Tools Gemini | JSON Schema crudo | `FunctionDeclarationSchema` con `SchemaType` |
| Tools LangChain | `Record<string, unknown>` | `BindToolsInput[]` |
| Step budget | No expuesto | `maxSteps` en `ai@4` (default 1); `stopWhen` en `ai@5+` |

Evidencia adicional:

- En `ai@4`, `maxSteps` vale `1` por defecto. El README no lo configura; `prepareStep` se ejecuta una vez con `steps=[]` y el loop shield nunca dispara.
- `tests/integration.test.ts` construye tools con `parameters: {}`; el SDK real llama a `zodToJsonSchema({})`, que lanza `TypeError`. Los tests pasan porque nunca llaman a `generateText`.
- `tsc --noEmit` sale 0 solo porque cada frontera con el proveedor es `unknown`; no demuestra compatibilidad.
- `refreshGate` llama a `_setState` (guard + `onTransition`), así que es una transición, no un refresh; un guard que bloquea lanza.

## 6. Comparativa

| Alternativa | Qué resuelve | Qué ofrece para este problema | Coste / límite |
|---|---|---|---|
| **Vercel AI SDK 7** | Tool calling, multi-step, providers, aprobaciones | `prepareStep`, `activeTools`, `stopWhen`, `toolChoice:'none'`, `toolApproval` | Ya es dependencia en muchos stacks; API grande |
| **OpenAI Agents SDK** | Agentes, tools, guardrails, sesiones, handoffs | `isEnabled`, `needsApproval`, guardrails, `allowedCallers` | OpenAI-céntrico; runtime propio |
| **LangGraph** | Orquestación de grafos, persistencia, HITL | `recursionLimit`/`GraphRecursionError`, `interrupt()`, `ToolNode` | Más pesado; modelo mental de grafos |
| **XState** | Statecharts, actores, guards | Semántica FSM real, guards puros, visualización | No es específico de IA; más concepto |
| **Mastra** | Runtime de agentes, workflows, memoria, HITL | Agentes, tools, workflows, human-in-the-loop | Framework completo; más complejidad |
| **Código propio** | `toolsByState[state]` + Zod + `activeTools` | Control total, cero dependencias nuevas | Hay que escribirlo y testearlo |

Conclusión: reactive-fsm no compite como framework de agentes ni como FSM. Su único nicho defendible es una política pequeña y provider-agnóstica de disponibilidad de herramientas por estado, con un presupuesto de llamadas. Hoy no demuestra que reduzca complejidad frente a `activeTools` de AI SDK 7, `isEnabled` de OpenAI Agents SDK o 10 líneas propias.

```ts
it('rechaza una transición async obsoleta', async () => {
  let release!: (v: boolean) => void;
  const pending = new Promise<boolean>((r) => { release = r; });
  const fsm = createFSM({
    initialState: 'A',
    states: ['A', 'B', 'C'],
    tools: {},
    guard: (_from, to) => (to === 'B' ? pending : true),
  });

  const first = fsm.transitionToAsync('B');
  fsm.transitionTo('C');
  release(true);
  await first;

  expect(fsm.currentState).toBe('C');
});
```
